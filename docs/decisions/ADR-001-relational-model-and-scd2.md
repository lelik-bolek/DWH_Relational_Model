# ADR-001: Выбор модели историзации (SCD Type 2) и суррогатных ключей в реляционной витрине

## Статус
Принято

## Контекст
В рамках учебного проекта `DWH_Relational_Model` решается задача преобразования сырых, составных данных (`courses_0nf`) в аналитическую модель с сохранением истории изменений сущностей предметной области (студенты, преподаватели, курсы, города).

В процессе нормализации (0NF → 1NF → 2NF → 3NF) сущности были декомпозированы с выделением естественных бизнес-ключей (`student_email`, `course_name`, `teacher_email`, `city_name`). Однако бизнес-атрибуты со временем меняются (изменение фамилии или телефона студента, смена преподавателя курса, корректировка стоимости обучения, переименование или смена региона города). 

Требовалось определить подход к историзации измерений и способ их связывания с фактами заказов (`orders_3nf_fact`).

## Решение
1. **Применение Slowly Changing Dimensions Type 2 (SCD Type 2):**
   * Для историзируемых сущностей (`student_3nf_scd2`, `courses_3nf_scd2`, `teachers_3nf_scd2`, `cities_3nf_scd2`) используется интервальная версионность: поля `valid_from` (дата начала действия версии), `valid_to` (дата окончания, `9999-12-31` для активной записи) и логический флаг `is_current`.
   * При обновлении атрибута текущая версия закрывается текущей датой (`valid_to = CURRENT_DATE`, `is_current = false`), и вставляется новая строка с актуальными значениями (`valid_from = CURRENT_DATE`, `valid_to = '9999-12-31'`, `is_current = true`).

2. **Введение суррогатных ключей (Surrogate Keys):**
   * В качестве первичного ключа каждой версии записи используется суррогатный ключ типа `SERIAL` (`student_sk`, `course_sk`, `teacher_sk`, `city_sk`).
   * Естественный бизнес-ключ сохраняется в таблице для идентификации принадлежности версии конкретному бизнес-объекту.

3. **Гарантия уникальности активной версии:**
   * Контроль целостности на уровне СУБД обеспечивается частичным уникальным индексом:
     ```sql
     CREATE UNIQUE INDEX ... ON <table> (business_key) WHERE is_current = true;
     ```

4. **Связывание с таблицей фактов (`orders_3nf_fact`):**
   * Таблица фактов ссылается не на естественный бизнес-ключ, а непосредственно на суррогатный ключ версии измерения (`student_sk`, `course_sk`). Это фиксирует точное состояние сущностей на момент оформления заказа без необходимости ретроспективных джойнов по интервалам дат.

## Последствия (Trade-offs)

### Положительные
* **Точность аналитических отчетов:** Факт транзакции навсегда привязан к конкретному срезу атрибутов (например, стоимости курса и контактным данным студента на дату покупки).
* **Консистентность текущего состояния:** Частичный индекс исключает возникновение двух активных версий одной сущности на уровне ограничений БД.
* **Производительность запросов:** Джойны по целочисленным суррогатным ключам (`INT`/`SERIAL`) эффективнее соединений по составным текстовым ключам.

### Компромиссы и ограничения (Cons / Known Limitations)
* **Процедурная сложность обновления:** Закрытие старой версии и вставка новой требуют строго согласованных скриптов обновления (`update_*_3nf_scd2.sql`) либо транзакционного блока.
* **Каскад версий:** Изменение атрибута родительской сущности (например, города) требует контроля версий в зависимой сущности (студент), если связь построена через суррогатный ключ `city_sk`.
